This quotation covers a full migration of CaterFlow's data layer off Sanity CMS onto MongoDB only — removing Sanity Studio, the Sanity dataset, and all Sanity dependencies from the live application, including rebuilding authentication, file/image storage, and an admin data-browsing capability to replace what Sanity Studio currently provides. Scope was estimated directly from the codebase (see below), and is offered here as a fixed project fee rather than open-ended hourly billing, at a discounted project rate given the size and duration of the engagement.

Why this is a big job (scope found in the codebase)

  • The Next.js app currently reads/writes Sanity in 64 files, primarily the entire API layer (54 route files) — there are ~194 GROQ queries and ~211 Sanity fetch calls to rewrite individually as MongoDB queries/aggregations, since GROQ's reference joins have no drop-in equivalent.
  • Sanity Studio defines 24 schema/document types (StockItem, PurchaseOrder, GoodsReceipt, InventoryCount, DispatchLog, InternalTransfer, StockAdjustment, Supplier, Site, AppUser, and more) with relational references between them — these need to be redesigned as MongoDB collections with an equivalent referential-integrity strategy.
  • Login/auth is backed by Sanity (the AppUser document type) — this migration includes rebuilding authentication end-to-end, not just moving operational data.
  • The current production dataset holds roughly 24,800+ documents to migrate and validate (601 stock items, 34 users, 18 bins, 17 suppliers, 16 categories, 8 sites, plus thousands of nested transaction records).
  • Sanity's file/image CDN pipeline needs a replacement storage provider (e.g. S3, Cloudinary, or UploadThing), and Sanity Studio's admin editing UI needs at least a minimal equivalent so data can still be browsed/corrected without direct database access.
  • The app already has a separate, narrow MongoDB integration (used only for the Archive Run History feature) — this gives us working connection/driver plumbing and ETL script patterns to build on, but none of the live operational data is modeled in Mongo today.
